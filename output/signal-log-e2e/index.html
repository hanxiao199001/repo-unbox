拆开 SIGNAL LOG：一个深空留言板是怎么运转的

01

按下 Transmit 之后

你在左边的表单里打了一句话，点了那个写着 Transmit 的按钮。这一模块要做的，就是把这几乎看不见的一瞬间拉长、拆开，看看这句话到底走了哪几步，才变成右边那条带着信号强度的新记录。

这东西到底是什么

SIGNAL LOG 是一个带着深空电台外壳的留言板。首页左边是一张写着Transmit的表单，右边是一条不断滚动的日志。你在 Message 里打一句话、点一下 Transmit，几乎同一瞬间，右边"Live Log"那栏就会多出一条新记录，旁边还带着一个类似"Signal 87%"的百分比。

这条留言最终会落进一个叫 signal-log.db 的文件里——那才是真正意义上的"发出去"：刷新页面、关掉浏览器，它都还在那儿。这一路走过的几个文件，就是接下来五个模块要一个个拆开看的东西。

✦

从结局往回看

你已经知道结局了——那条留言确实出现在了列表里。这一模块不是要告诉你"会发生什么"，而是告诉你"凭什么会发生"。悬念在后面，不在前面。

第一站：浏览器先把你打的字捆成一个包裹

点击 Transmit 按钮触发的第一件事，发生在 public/app.js 里。这个文件负责把表单里的几个输入框读出来，捆成一个统一的payload，然后再送出去。

public/app.js:192-199

  const payload = {
    callsign: form.callsign.value,
    origin: form.origin.value,
    message: form.message.value,
    humanAnswer: form.humanAnswer.value,
    humanToken: state.humanToken,
    website: form.website.value
  };

先造一个叫 payload 的包裹，接下来几行都是往里面装东西。

callsign 和 origin 直接从表单输入框里读，用户没填就是空字符串，谁都不强求。

message 是这条留言真正的内容，同样直接读输入框的值，一个字都还没被改过。

humanAnswer 是用户在人类验证那道加法题里填的答案。

humanToken 却不是从输入框来的——它是页面早先问服务器要来的一次性凭证，存在一个叫 state 的对象里。

website 是一个用户看不见的陷阱字段，专门留给自动灌水的机器人，人手动填表单永远碰不到它。

捆好包裹之后，app.js 会调用一个叫fetch的浏览器内置函数，带着这份 payload，往服务器发一次POST请求。而在这一步真正把请求送出去之前，代码里还有await，意思是页面会老老实实等服务器给个答复，不会自己先往下走。

点着走一遍这个包裹的完整旅程——从你打字，到它真正落进数据库，再到你在屏幕上看见结果。

第三站：server.js 里都过了哪些关卡

包裹到达服务器之后，并不会被直接相信。接口 /api/messages 背后的函数，会重新校验一遍每一样东西——它从来不假设浏览器那边已经查过了。

server.js:158-169

app.post('/api/messages', enforcePostRateLimit, (req, res) => {
  const payload = req.body || {};

  const callsign = normalizeText(payload.callsign, 24);
  const origin = normalizeText(payload.origin, 32);
  const message = normalizeText(payload.message, 300);
  const humanAnswer = normalizeText(payload.humanAnswer, 16);
  const humanToken = normalizeText(payload.humanToken, 64);
  const website = normalizeText(payload.website, 128);

  if (website) {
    return jsonError(res, 400, 'Spam detected.');

这是这条路的入口：只要有人往 /api/messages 发 POST 请求，都会先经过 enforcePostRateLimit 这一道频率检查，通过了才轮到这个函数。

req.body 是请求里带来的那个包裹，万一什么都没带，就退而求其次用一个空对象顶上，不至于直接报错。

接下来六行，把包裹里的每一样东西都过一遍 normalizeText——去掉多余空格、掐掉超出长度限制的部分。

website 这一栏，人是看不见的，只有自动灌水的脚本才会傻乎乎地把它填上。

只要 website 有内容，就直接判定是垃圾信息，请求到此为止，根本不会碰到数据库。

这里的 400 是一种状态码，意思是"你发来的东西本身有问题，我懒得往下处理了"，跟服务器自己出没出错完全是两码事——这个区分在模块五还会再展开。

小结

一句话捋一遍：app.js 把表单捆成 payload 发出去，server.js 重新校验一遍，通过了才会交给 db.js 落盘，最后 app.js 再把最新的列表画出来。三个文件，各管一段，谁都不完全信任谁。

如果有人绕开网页表单，直接用工具往 /api/messages 发一个 message 是空字符串的请求，会发生什么？

用你自己的话说一遍：你在 Message 里打字、点下 Transmit 之后，这句话依次经过了哪些文件，才变成右边 Live Log 里的一条新记录？

  • 提到了 app.js 先把 callsign、origin、message 捆成一个 payload
  • 说出了请求走的是 POST /api/messages 这条路
  • 提到 server.js 会重新校验一遍，不是只信任浏览器
  • 说清楚只有 db.js 真正碰那个数据库文件

02

这个项目里都有谁

上一模块跟着一条留言走了一遍全程，路过了好几个文件名。这一模块停下来，把这几个文件当成几个角色，一个个认清楚：谁负责收发、谁只管硬盘、谁只管好看。

五个文件，五个分工

SIGNAL LOG 一共只有五个自己写的文件，就像一个开在网上的快递驿站：有人在窗口收件，有人在后头的仓库码货，还有人负责把门面装修得像回事。分工非常干净——每个文件只管一件事。

public/app.js

前台窗口。收你打的字，画你看到的页面，自己不留东西——关掉标签页，它记的一切都没了。

S

server.js

驿站的分拣员。谁发来的东西，先查一遍、分好类，再决定往哪儿送，自己从不留货。

D

后头的仓库。整个项目里只有它真正碰硬盘，货物进出都要经过它的账本。

H

public/index.html

门面的骨架。表单有几个输入框、按钮摆在哪，都是它说了算，但它不管好不好看。

C

门面的装修。深蓝底色、荧光青边框，这一整套深空电台的味道全是它调出来的。

server.js：只负责派活，不留一件东西

server.js 用的是一个叫Express的框架。它的核心工作就是给每一条路由安排好该由哪段代码来接。下面这一段就是全项目里最短的一条路由——专门用来发一道人类验证题。

server.js:143-146

app.get('/api/human-check', (_req, res) => {
  const challenge = makeHumanCheck();
  return res.json(challenge);
});

这一行声明：只要有人拿 GET 方式访问 /api/human-check，就交给这个函数处理。

调用 makeHumanCheck，生成一道新的加法题和一次性凭证，自己不参与出题逻辑。

把结果转成一份大家能读的回复直接送出去——server.js 全程没有把这道题存进硬盘，转手就交出去了。

你会发现 server.js 里几乎每一条路由都是这个套路：接一下、查一下、转手交给别人，自己从不留东西。这也是为什么调试的时候，"数据丢了"这种问题从来不该先怪它。

db.js：不只是存东西，还会算账

整个项目只有 db.js 会碰那个叫 signal-log.db 的文件，用的是一个叫SQLite的轻量数据库。但它不只是"存进去、读出来"这么简单——每条新留言送到它手上时，它还会顺手给这条留言算一个信号强度。

db.js:95-100

function computeStrength(message, id) {
  const len = message.length;
  const base = Math.min(85, 20 + Math.floor((len / 300) * 65));
  const noise = hashInt(id) % 16;
  return Math.max(0, Math.min(100, base + noise));
}

先量出这条留言有多少个字符，字越多，等一下算出来的基础分越高。

base 是基础信号强度，最高封顶在 85，留言越长越接近这个上限。

noise 是拿这条记录的 id 算出来的一个 0 到 15 之间的余数，给每条留言添一点看起来随机的浮动。

最后把 base 和 noise 加起来，夹在 0 到 100 之间，这就是你在页面上看到的那个百分比。

ℹ

这个数字不是真的信号

signal-log.db 里存的这个 strength，本质上只是根据留言长度和 id 算出来的一个装饰性数字，跟真实的电台信号毫无关系——它的作用是让这个虚构的深空电台看起来更像那么回事。

前端三件套：骨架、装修、行为，一层层叠上去

public 目录下的三个文件，正好对应网页的三层：index.html 是DOM结构，styles.css 管外观，app.js 管交互。切一下下面这几个标签，看看同一个表单在不同阶段长什么样。

只有骨架：能看到表单和按钮，样式全无，点了也没有任何反应。
骨架加上装修：深空视觉出来了，但按钮和输入框仍然是摆设。
骨架、装修、行为三层叠满：点击 Transmit 真的会发出请求，页面才算完整地"活"了起来。

03

搜索框怎么问到数据库

你在搜索框里打了"orbit"两个字，什么都没点，列表却自己刷新了。这一模块跟着这几个字，看它怎么变成一句网址、又怎么变成一条能在数据库里查东西的语句。

你打字，它不用你点确认

Live Log 上方有一个搜索框，左边还有四个筛选按钮：ALL、EARTH、UNKNOWN、CUSTOM。你在搜索框里打字，停顿了大约三分之一秒之后，列表会自己刷新——这个"停顿一下才出手"的动作叫debounce（防抖）。

这就好比食堂的打饭窗口：你不用先递交一份正式申请，说一句"我要这个"，师傅就动手了。搜索框背后的接口 GET /api/messages，就是那个打饭窗口——你说清楚要什么，师傅按你说的给，具体怎么从后厨的一大锅菜里舀出来，你不需要知道。

第一站：你打的字变成一段网址

app.js 里有个专门负责去要数据的函数，它先把你现在的搜索词、筛选条件，统统塞进一个叫URLSearchParams的工具里。

public/app.js:138-148

async function loadMessages({ reset = false } = {}) {
  if (state.loading) return;
  state.loading = true;
  if (reset) state.offset = 0;

  const qs = new URLSearchParams({
    limit: String(state.limit),
    offset: String(state.offset),
    q: state.query,
    origin: originFilterValue()
  });

如果上一次请求还没回来，直接放弃这一次，免得同时飞出去两份一样的请求。

reset 为真，说明这是一次全新查询（比如换了筛选条件），要把翻页的位置清零。

limit 和 offset 决定这次要第几页、每页拿多少条，都转成字符串塞进去。

q 就是搜索框里那几个字，origin 是当前选中的筛选条件算出来的值。

这几行执行完，qs 变量就是一段现成的网址参数，形如 limit=50&offset=0&q=orbit&origin=，紧接着就会被拼在 /api/messages? 后面发出去。

第二站：服务器把网址参数拆开来读

这段参数飞到服务器之后，server.js 要把它从一串文字，重新拆成几个能用的变量。

server.js:148-156

app.get('/api/messages', (req, res) => {
  const limit = Math.max(1, Math.min(50, Number.parseInt(req.query.limit, 10) || 50));
  const offset = Math.max(0, Number.parseInt(req.query.offset, 10) || 0);
  const query = normalizeText(req.query.q, 100);
  const origin = normalizeText(req.query.origin, 64);

  const result = listMessages({ limit, offset, query, origin });
  return res.json(result);
});

req.query 就是刚才那段网址参数被 Express 自动解析出来的对象，字段名跟前面 qs 里的一一对应。

limit 被夹在 1 到 50 之间——就算有人手动把网址改成 limit=99999，服务器也不会照单全收。

query 和 origin 依旧要走一遍 normalizeText，跟模块一里校验留言用的是同一个函数。

整理干净之后，转手交给 db.js 里的 listMessages，自己不碰任何跟 SQL 有关的东西。

第三站：这些条件拼成一句能查数据库的话

真正会写SQL语句的，只有 db.js。它会根据你有没有搜索词、有没有选筛选条件，一段一段地往一句大的查询语句上拼接。

db.js:69-80

const listMessagesStmtFactory = ({ hasQuery, hasOrigin, unknownOriginOnly }) => {
  let sql = `
    SELECT id, created_at, callsign, origin, message, strength
    FROM messages
    WHERE 1=1
  `;
  if (hasQuery) sql += ` AND message LIKE @q`;
  if (unknownOriginOnly) {
    sql += ` AND (origin IS NULL OR TRIM(origin) = '' OR LOWER(origin) LIKE '%unknown%')`;
  } else if (hasOrigin) {
    sql += ` AND LOWER(COALESCE(origin, '')) LIKE @origin`;
  }

先写一句永远成立的 WHERE 1=1，后面不管加多少条件，都只需要用 AND 往上接，不用纠结第一条要不要写 WHERE。

有搜索词的话，加上一句用 LIKE 做模糊匹配的条件，@q 是一个占位符，真正的值稍后才会填进去。

选了 UNKNOWN 筛选，就专门找 origin 是空的、或者字面上带着 unknown 的那些记录。

选了别的具体来源，就用 LIKE 做一次大小写不敏感的模糊匹配。

⚠

占位符不是可有可无的讲究

代码里的 @q、@origin 叫参数占位符，真正的值是后面单独传进去的，而不是直接拼进 SQL 字符串里。如果换成直接拼接用户输入的文字，别人就可能在搜索框里打出一段能篡改整句查询的文字——这种攻击手法就是常说的 SQL 注入，占位符正是用来挡住它的。

串起来看一眼

→
2URLSearchParams

五步看着简单，但每一步都换了一次"语言"：先是你脑子里的关键词，变成网址参数，再变成服务器手里的几个变量，最后变成数据库能听懂的 SQL，查完再一路翻译回来，变成你眼前的一条条记录。

小结

你确定数据库里有一条包含"orbit"的留言，但搜索框搜"orbit"什么都搜不到。你会先打开哪个文件确认？

你朋友问你"这个网站的搜索到底是怎么工作的"，用不超过三句话讲给他听，不许用"接口""数据库"这类术语。

  • 说清楚了打字之后不是立刻查，而是停顿一下才查（对应 debounce 这个词）
  • 说明了搜索词最终是走网址传过去的，而不是凭空猜出来的
  • 提到了真正去大量数据里挑记录的那一步，不是浏览器自己做的

04

写代码的人在防着谁

这个网站是公开在互联网上的，任何人都能往 /api/messages 发请求，不只是坐在浏览器前的你。这一模块看看原作者留了哪几道关卡，专门挡那些不怀好意的请求。

如果没人守门，会发生什么

一个对外开放的留言板，天生要面对三类麻烦：自动脚本一秒刷几百条灌水消息、有人在留言里塞一段能在别人浏览器里执行的代码、还有人干脆想篡改数据库删掉别人的话。这些请求排着队想挤进 /api/messages，就像地铁早高峰的进站口，得一道一道关卡过滤，才能保证站台上是安全的。

server.js 里请求先要经过的第一关，是一个叫Helmet的中间件。

server.js:15-26

app.use(helmet({
  crossOriginEmbedderPolicy: false,
  contentSecurityPolicy: {
    directives: {
      defaultSrc: ["'self'"],
      scriptSrc: ["'self'"],
      styleSrc: ["'self'", "'unsafe-inline'"],
      imgSrc: ["'self'", 'data:'],
      connectSrc: ["'self'"],
      objectSrc: ["'none'"],
      baseUri: ["'self'"],
      formAction: ["'self'"]

app.use 表示"每一个请求都要先过这一关"，不管它最终要去哪条路由。

这一整段是CSP的配置，等于告诉浏览器"这个页面的脚本、样式、图片只准从自己这个网站加载"。

scriptSrc 只写了 'self'，意味着任何想从别的网站偷偷插进来执行的脚本，浏览器直接就不会跑它。

connectSrc 同理只准连自己——就算页面被塞进了坏代码，它也没法偷偷把你的数据发到别的服务器。

第二关：一小时最多发十条

过了 Helmet 这一关，POST 请求还要过一道专门为 /api/messages 设的中间件，防的是同一个人（更准确地说，同一个 IP）在短时间里疯狂刷屏。

server.js:81-92

function enforcePostRateLimit(req, res, next) {
  const ip = getClientIp(req);
  const now = Date.now();
  const entry = postRateByIp.get(ip) || { recent: [], lastPostAt: 0 };
  entry.recent = entry.recent.filter((ts) => now - ts <= rateWindowMs);

  if (entry.lastPostAt && now - entry.lastPostAt < minGapMs) {
    return jsonError(res, 429, 'Rate limit: wait at least 10 seconds between transmissions.');
  }
  if (entry.recent.length >= maxPostsPerWindow) {
    return jsonError(res, 429, 'Rate limit: maximum 10 transmissions per hour.');
  }

先按 IP 地址找出这个人最近的发送记录，一个内存里的 Map 结构，谁都没有单独的账号。

把一小时之外的旧记录过滤掉，只留下窗口期内还算数的那些。

距离上一次发送不满 10 秒，直接用 429 拒绝——这个状态码的意思就是"你发得太快了"。

一小时内已经发过 10 条，同样用 429 拒绝，逻辑上跟前一条是两道独立的关卡。

⚠

这道关卡关服务器重启就没了

postRateByIp 只是一个存在内存里的普通对象，不是数据库表。服务器一重启，所有人的发送记录全部清零——这也是 README 里强调"不把 IP 存进 SQLite"的原因：这份记录本来就只是临时挡一挡，不是要长期追踪谁。

第三关：证明你是人，不是脚本

光靠限流还不够——一个脚本完全可以每 11 秒发一条，慢慢刷屏。所以真正发消息之前，页面会先问服务器要一道随机的加法题。

server.js:53-60

function makeHumanCheck() {
  const a = randomInt(2, 12);
  const b = randomInt(1, 12);
  const token = `${Date.now().toString(36)}-${Math.random().toString(36).slice(2, 12)}`;
  const answer = String(a + b);
  humanChecks.set(token, { answer, expiresAt: Date.now() + humanCheckTTL });
  return { token, question: `${a} + ${b} = ?` };
}

随机出两个数字，凑成一道加法题，对一个真人来说毫不费力，对没有专门适配的脚本却是道坎。

token 是这道题专属的一次性凭证，混进了当前时间和一段随机字符，几乎不会跟别的题撞上。

正确答案连同这道题的TTL（有效期）一起，存进服务器内存里的 humanChecks，等着后面用 humanToken 来对答案。

只把题目和 token 送回前端，正确答案永远不会出现在发给浏览器的数据里。

还记得模块一里 server.js:158-169 那段代码吗？那里的 website 字段就是另一道关卡——honeypot（蜜罐）字段，人根本看不到它，只有不看页面样式、直接把每个输入框都填一遍的脚本才会中招。

第四关：前端画页面的时候也要挡一次

就算前面几关都被绕过、一条带着恶意代码的留言真的存进了数据库，app.js 在把它画到页面上时，还留了最后一道防线。

public/app.js:96-103

function renderItems(adminMode = false) {
  if (!dom.logFeed) return;
  dom.logFeed.innerHTML = state.items.map((item) => entryTemplate(item, adminMode)).join('');
  const blocks = dom.logFeed.querySelectorAll('.entry');
  blocks.forEach((entry, idx) => {
    const textEl = entry.querySelector('.message-text');
    textEl.textContent = state.items[idx].message;
  });

先用 innerHTML 一次性把外层卡片、按钮这些"骨架"画出来——这部分内容都是代码里写死的，不是用户能改的。

但留言正文没有跟着骨架一起用 innerHTML 塞进去，而是单独挑出来，逐条重新赋值。

关键就在这句 textContent：留言里就算写了一段像代码的文字，也只会被当成一串普普通通的字显示出来，不会被浏览器当真去执行。

✦

这道防线有个通用的名字

如果用户能提交的文字，被原样当成网页代码执行，攻击者就能在别人的浏览器里跑任意脚本——这类攻击统称XSS。这个项目挡它的办法很朴素：凡是用户自己写的内容，一律用 textContent 显示，绝不让浏览器把它当成标签解析。

报错时先看哪

你在 /admin 页面填错了管理员令牌，点了 Delete，屏幕右下角弹出一行红字："Unauthorized admin token."。这一模块拆开这行字背后的机制，教你看到报错之后，第一反应该往哪个文件里翻。

同一句"出错了"，其实分好几种

自助取件柜上贴的提示语通常分好几种：取件码打错了、格子本来就是空的、机器本身坏了——三件完全不同的事，处理方式也完全不一样。SIGNAL LOG 的报错也是这个道理，全部用一个统一的状态码加一句文字来表达，但意思天差地别。

✦

先分清是谁的错

4 开头的状态码基本都是"你这边的问题"——密码错了、留言太长了、格式不对；5 开头才是"服务器这边真的出故障了"。分清这一点，你才知道该改自己的输入，还是该去查后端代码。

同一个把关函数，两种完全不同的报错

DELETE 一条留言之前，请求要先过 adminGuard 这道关卡。它短短几行，却给出了两种意思完全不同的拒绝。

server.js:132-141

function adminGuard(req, res, next) {
  if (!ADMIN_TOKEN) {
    return jsonError(res, 500, 'Admin token is not configured on server.');
  }
  const token = req.headers['x-admin-token'];
  if (!token || token !== ADMIN_TOKEN) {
    return jsonError(res, 401, 'Unauthorized admin token.');
  }
  return next();
}

如果服务器启动时压根没设置 ADMIN_TOKEN 这个环境变量，直接用 500 报错——这是服务器自己没配置好，跟你填没填令牌毫无关系。

从请求头里读出你在 /admin 页面填的令牌。

令牌是空的，或者跟服务器上配置的对不上，用 401 拒绝——这次是"你"的问题，令牌不对。

前面两关都过了，next() 表示放行，交给真正删除数据的那段代码。

同样都是"不让你删"，500 和 401 指向完全不同的排查方向：看到 500，该去检查 .env 文件里有没有 ADMIN_TOKEN；看到 401，该回头检查自己填的令牌对不对。

路走错了，或者哪儿都没接住

如果请求压根不属于任何一条已知路由呢？比如你手滑把网址打成了 /api/message，少了一个 s。server.js 末尾留了两道兜底。

server.js:285-289

app.use('/api', (_req, res) => jsonError(res, 404, 'API route not found.'));
app.use((err, _req, res, _next) => {
  console.error(err);
  return jsonError(res, 500, 'Internal server error.');
});

凡是以 /api 开头、但前面所有路由都没接住的请求，最后都会落到这一句，统一回一个 404——意思是"这条路根本不存在"。

下面这个函数专门接"代码运行到一半自己炸了"的情况，先把真正的错误打印到服务器自己的日志里，方便开发者事后查。

但绝不会把内部的错误细节原样发给用户，回的永远是一句笼统的 Internal server error——这是为了不把服务器内部的实现细节暴露给外面。

前端怎么把这句报错捞出来，显示给你看

服务器回的那句 { "error": "..." }，最终要变成你在页面上看见的那个红色提示，中间要经过 app.js 里一个统一的请求函数。

public/app.js:123-134

async function apiFetch(url, options = {}) {
  const res = await fetch(url, {
    headers: {
      'Content-Type': 'application/json',
      ...(options.headers || {})
    },
    ...options
  });
  const data = await res.json().catch(() => ({}));
  if (!res.ok) {
    throw new Error(data.error || 'Request failed');
  }

全项目所有跟服务器的通信都走这一个函数，好处是错误处理的逻辑只需要写这一份。

先把服务器回的内容尝试解析成一个对象，就算解析失败也不让整个页面崩掉，退而求其次给个空对象。

res.ok 是 fetch 自带的一个判断：状态码在 200 到 299 之间才算真正成功。

不成功就主动抛出一个错误，内容优先用服务器给的那句 error 文字——这就是为什么你在页面上看到的提示，跟服务器代码里写的那句英文一字不差。

Admin token is not configured on server.

状态码 500。服务器启动时没有读到 ADMIN_TOKEN 这个环境变量，通常是 .env 文件没建、或者忘了在里面填这一项。对 AI 说："帮我检查 .env 文件有没有正确设置 ADMIN_TOKEN，并确认 server.js 启动时能读到它。"

Unauthorized admin token.

状态码 401。/admin 页面里填的令牌，跟服务器 .env 文件里的 ADMIN_TOKEN 对不上。对 AI 说："我在管理页面填的令牌一直提示 Unauthorized，帮我确认这两边的值到底哪里不一样。"

Rate limit: maximum 10 transmissions per hour.

状态码 429。同一个 IP 一小时内发了超过 10 条留言，触发了 enforcePostRateLimit 里的次数限制。这是设计好的行为，不是故障，对 AI 说："帮我把这个限流的上限从 10 条改成 20 条，在哪个文件改。"
