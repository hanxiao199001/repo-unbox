搜索框怎么问到数据库

你在搜索框里打了"orbit"两个字，什么都没点，列表却自己刷新了。这一模块跟着这几个字，看它怎么变成一句网址、又怎么变成一条能在数据库里查东西的语句。

你打字，它不用你点确认

Live Log 上方有一个搜索框，左边还有四个筛选按钮：ALL、EARTH、UNKNOWN、CUSTOM。你在搜索框里打字，停顿了大约三分之一秒之后，列表会自己刷新——这个"停顿一下才出手"的动作叫debounce（防抖）。

这就好比食堂的打饭窗口：你不用先递交一份正式申请，说一句"我要这个"，师傅就动手了。搜索框背后的接口 GET /api/messages，就是那个打饭窗口——你说清楚要什么，师傅按你说的给，具体怎么从后厨的一大锅菜里舀出来，你不需要知道。

第一站：你打的字变成一段网址

app.js 里有个专门负责去要数据的函数，它先把你现在的搜索词、筛选条件，统统塞进一个叫URLSearchParams的工具里。

public/app.js:138-148

async function loadMessages({ reset = false } = {}) {
  if (state.loading) return;
  state.loading = true;
  if (reset) state.offset = 0;

  const qs = new URLSearchParams({
    limit: String(state.limit),
    offset: String(state.offset),
    q: state.query,
    origin: originFilterValue()
  });

如果上一次请求还没回来，直接放弃这一次，免得同时飞出去两份一样的请求。

reset 为真，说明这是一次全新查询（比如换了筛选条件），要把翻页的位置清零。

limit 和 offset 决定这次要第几页、每页拿多少条，都转成字符串塞进去。

q 就是搜索框里那几个字，origin 是当前选中的筛选条件算出来的值。

这几行执行完，qs 变量就是一段现成的网址参数，形如 limit=50&offset=0&q=orbit&origin=，紧接着就会被拼在 /api/messages? 后面发出去。

第二站：服务器把网址参数拆开来读

这段参数飞到服务器之后，server.js 要把它从一串文字，重新拆成几个能用的变量。

server.js:148-156

app.get('/api/messages', (req, res) => {
  const limit = Math.max(1, Math.min(50, Number.parseInt(req.query.limit, 10) || 50));
  const offset = Math.max(0, Number.parseInt(req.query.offset, 10) || 0);
  const query = normalizeText(req.query.q, 100);
  const origin = normalizeText(req.query.origin, 64);

  const result = listMessages({ limit, offset, query, origin });
  return res.json(result);
});

req.query 就是刚才那段网址参数被 Express 自动解析出来的对象，字段名跟前面 qs 里的一一对应。

limit 被夹在 1 到 50 之间——就算有人手动把网址改成 limit=99999，服务器也不会照单全收。

query 和 origin 依旧要走一遍 normalizeText，跟模块一里校验留言用的是同一个函数。

整理干净之后，转手交给 db.js 里的 listMessages，自己不碰任何跟 SQL 有关的东西。

第三站：这些条件拼成一句能查数据库的话

真正会写SQL语句的，只有 db.js。它会根据你有没有搜索词、有没有选筛选条件，一段一段地往一句大的查询语句上拼接。

db.js:69-80

const listMessagesStmtFactory = ({ hasQuery, hasOrigin, unknownOriginOnly }) => {
  let sql = `
    SELECT id, created_at, callsign, origin, message, strength
    FROM messages
    WHERE 1=1
  `;
  if (hasQuery) sql += ` AND message LIKE @q`;
  if (unknownOriginOnly) {
    sql += ` AND (origin IS NULL OR TRIM(origin) = '' OR LOWER(origin) LIKE '%unknown%')`;
  } else if (hasOrigin) {
    sql += ` AND LOWER(COALESCE(origin, '')) LIKE @origin`;
  }

先写一句永远成立的 WHERE 1=1，后面不管加多少条件，都只需要用 AND 往上接，不用纠结第一条要不要写 WHERE。

有搜索词的话，加上一句用 LIKE 做模糊匹配的条件，@q 是一个占位符，真正的值稍后才会填进去。

选了 UNKNOWN 筛选，就专门找 origin 是空的、或者字面上带着 unknown 的那些记录。

选了别的具体来源，就用 LIKE 做一次大小写不敏感的模糊匹配。

⚠

占位符不是可有可无的讲究

代码里的 @q、@origin 叫参数占位符，真正的值是后面单独传进去的，而不是直接拼进 SQL 字符串里。如果换成直接拼接用户输入的文字，别人就可能在搜索框里打出一段能篡改整句查询的文字——这种攻击手法就是常说的 SQL 注入，占位符正是用来挡住它的。

串起来看一眼

1你打字
→
2URLSearchParams
→
3req.query
→
4拼 SQL
→
5画回列表

五步看着简单，但每一步都换了一次"语言"：先是你脑子里的关键词，变成网址参数，再变成服务器手里的几个变量，最后变成数据库能听懂的 SQL，查完再一路翻译回来，变成你眼前的一条条记录。

小结

你确定数据库里有一条包含"orbit"的留言，但搜索框搜"orbit"什么都搜不到。你会先打开哪个文件确认？

你朋友问你"这个网站的搜索到底是怎么工作的"，用不超过三句话讲给他听，不许用"接口""数据库"这类术语。

  • 说清楚了打字之后不是立刻查，而是停顿一下才查（对应 debounce 这个词）
  • 说明了搜索词最终是走网址传过去的，而不是凭空猜出来的
  • 提到了真正去大量数据里挑记录的那一步，不是浏览器自己做的
