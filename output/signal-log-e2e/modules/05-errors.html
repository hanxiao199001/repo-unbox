报错时先看哪

你在 /admin 页面填错了管理员令牌，点了 Delete，屏幕右下角弹出一行红字："Unauthorized admin token."。这一模块拆开这行字背后的机制，教你看到报错之后，第一反应该往哪个文件里翻。

同一句"出错了"，其实分好几种

自助取件柜上贴的提示语通常分好几种：取件码打错了、格子本来就是空的、机器本身坏了——三件完全不同的事，处理方式也完全不一样。SIGNAL LOG 的报错也是这个道理，全部用一个统一的状态码加一句文字来表达，但意思天差地别。

✦

先分清是谁的错

4 开头的状态码基本都是"你这边的问题"——密码错了、留言太长了、格式不对；5 开头才是"服务器这边真的出故障了"。分清这一点，你才知道该改自己的输入，还是该去查后端代码。

同一个把关函数，两种完全不同的报错

DELETE 一条留言之前，请求要先过 adminGuard 这道关卡。它短短几行，却给出了两种意思完全不同的拒绝。

server.js:132-141

function adminGuard(req, res, next) {
  if (!ADMIN_TOKEN) {
    return jsonError(res, 500, 'Admin token is not configured on server.');
  }
  const token = req.headers['x-admin-token'];
  if (!token || token !== ADMIN_TOKEN) {
    return jsonError(res, 401, 'Unauthorized admin token.');
  }
  return next();
}

如果服务器启动时压根没设置 ADMIN_TOKEN 这个环境变量，直接用 500 报错——这是服务器自己没配置好，跟你填没填令牌毫无关系。

从请求头里读出你在 /admin 页面填的令牌。

令牌是空的，或者跟服务器上配置的对不上，用 401 拒绝——这次是"你"的问题，令牌不对。

前面两关都过了，next() 表示放行，交给真正删除数据的那段代码。

同样都是"不让你删"，500 和 401 指向完全不同的排查方向：看到 500，该去检查 .env 文件里有没有 ADMIN_TOKEN；看到 401，该回头检查自己填的令牌对不对。

路走错了，或者哪儿都没接住

如果请求压根不属于任何一条已知路由呢？比如你手滑把网址打成了 /api/message，少了一个 s。server.js 末尾留了两道兜底。

server.js:285-289

app.use('/api', (_req, res) => jsonError(res, 404, 'API route not found.'));
app.use((err, _req, res, _next) => {
  console.error(err);
  return jsonError(res, 500, 'Internal server error.');
});

凡是以 /api 开头、但前面所有路由都没接住的请求，最后都会落到这一句，统一回一个 404——意思是"这条路根本不存在"。

下面这个函数专门接"代码运行到一半自己炸了"的情况，先把真正的错误打印到服务器自己的日志里，方便开发者事后查。

但绝不会把内部的错误细节原样发给用户，回的永远是一句笼统的 Internal server error——这是为了不把服务器内部的实现细节暴露给外面。

前端怎么把这句报错捞出来，显示给你看

服务器回的那句 { "error": "..." }，最终要变成你在页面上看见的那个红色提示，中间要经过 app.js 里一个统一的请求函数。

public/app.js:123-134

async function apiFetch(url, options = {}) {
  const res = await fetch(url, {
    headers: {
      'Content-Type': 'application/json',
      ...(options.headers || {})
    },
    ...options
  });
  const data = await res.json().catch(() => ({}));
  if (!res.ok) {
    throw new Error(data.error || 'Request failed');
  }

全项目所有跟服务器的通信都走这一个函数，好处是错误处理的逻辑只需要写这一份。

先把服务器回的内容尝试解析成一个对象，就算解析失败也不让整个页面崩掉，退而求其次给个空对象。

res.ok 是 fetch 自带的一个判断：状态码在 200 到 299 之间才算真正成功。

不成功就主动抛出一个错误，内容优先用服务器给的那句 error 文字——这就是为什么你在页面上看到的提示，跟服务器代码里写的那句英文一字不差。

小结

看到报错先做三件事：看状态码是 4 开头还是 5 开头，判断该改自己还是该查后端；看报错文字，它十有八九能在 server.js 里用文字原样搜到，直接定位到是哪一句 jsonError；最后看浏览器控制台，确认前端有没有把这句话正确地捞出来显示。

你在 /admin 页面填了令牌点 Delete，收到的报错是 500 加一句"Admin token is not configured on server."，你会先去哪里查？

你想让报错信息更明确一点，比如把"Message is required."换成能说明是哪个字段出问题的更详细提示。把你会对 AI 说的那句指令原样写出来。

  • 点名了要改 server.js 里 jsonError 抛出的具体文字
  • 说清楚了这个改动不影响状态码本身，只改文字内容
  • 提到了前端 apiFetch 会原样把这句新文字显示出来，不用额外改 app.js

你最可能撞上的报错

下面几条都是这个项目自己代码里写死的报错原文，一字不差——遇到的时候直接把整行拿去问 AI 就行。

Admin token is not configured on server.

状态码 500。服务器启动时没有读到 ADMIN_TOKEN 这个环境变量，通常是 .env 文件没建、或者忘了在里面填这一项。对 AI 说："帮我检查 .env 文件有没有正确设置 ADMIN_TOKEN，并确认 server.js 启动时能读到它。"

Unauthorized admin token.

状态码 401。/admin 页面里填的令牌，跟服务器 .env 文件里的 ADMIN_TOKEN 对不上。对 AI 说："我在管理页面填的令牌一直提示 Unauthorized，帮我确认这两边的值到底哪里不一样。"

Rate limit: maximum 10 transmissions per hour.

状态码 429。同一个 IP 一小时内发了超过 10 条留言，触发了 enforcePostRateLimit 里的次数限制。这是设计好的行为，不是故障，对 AI 说："帮我把这个限流的上限从 10 条改成 20 条，在哪个文件改。"

Error: Cannot find module 'express'

如果克隆下项目之后没有先执行 npm install 就直接运行 npm start，终端通常会报出类似这样"找不到某个模块"的错误。对 AI 说："我执行 npm start 报了 Cannot find module 的错误，是不是还没装依赖，帮我确认该跑哪条命令。"
