04

写代码的人在防着谁

这个网站是公开在互联网上的，任何人都能往 /api/messages 发请求，不只是坐在浏览器前的你。这一模块看看原作者留了哪几道关卡，专门挡那些不怀好意的请求。

如果没人守门，会发生什么

一个对外开放的留言板，天生要面对三类麻烦：自动脚本一秒刷几百条灌水消息、有人在留言里塞一段能在别人浏览器里执行的代码、还有人干脆想篡改数据库删掉别人的话。这些请求排着队想挤进 /api/messages，就像地铁早高峰的进站口，得一道一道关卡过滤，才能保证站台上是安全的。

server.js 里请求先要经过的第一关，是一个叫Helmet的中间件。

server.js:15-26

app.use(helmet({
  crossOriginEmbedderPolicy: false,
  contentSecurityPolicy: {
    directives: {
      defaultSrc: ["'self'"],
      scriptSrc: ["'self'"],
      styleSrc: ["'self'", "'unsafe-inline'"],
      imgSrc: ["'self'", 'data:'],
      connectSrc: ["'self'"],
      objectSrc: ["'none'"],
      baseUri: ["'self'"],
      formAction: ["'self'"]

app.use 表示"每一个请求都要先过这一关"，不管它最终要去哪条路由。

这一整段是CSP的配置，等于告诉浏览器"这个页面的脚本、样式、图片只准从自己这个网站加载"。

scriptSrc 只写了 'self'，意味着任何想从别的网站偷偷插进来执行的脚本，浏览器直接就不会跑它。

connectSrc 同理只准连自己——就算页面被塞进了坏代码，它也没法偷偷把你的数据发到别的服务器。

第二关：一小时最多发十条

过了 Helmet 这一关，POST 请求还要过一道专门为 /api/messages 设的中间件，防的是同一个人（更准确地说，同一个 IP）在短时间里疯狂刷屏。

server.js:81-92

function enforcePostRateLimit(req, res, next) {
  const ip = getClientIp(req);
  const now = Date.now();
  const entry = postRateByIp.get(ip) || { recent: [], lastPostAt: 0 };
  entry.recent = entry.recent.filter((ts) => now - ts <= rateWindowMs);

  if (entry.lastPostAt && now - entry.lastPostAt < minGapMs) {
    return jsonError(res, 429, 'Rate limit: wait at least 10 seconds between transmissions.');
  }
  if (entry.recent.length >= maxPostsPerWindow) {
    return jsonError(res, 429, 'Rate limit: maximum 10 transmissions per hour.');
  }

先按 IP 地址找出这个人最近的发送记录，一个内存里的 Map 结构，谁都没有单独的账号。

把一小时之外的旧记录过滤掉，只留下窗口期内还算数的那些。

距离上一次发送不满 10 秒，直接用 429 拒绝——这个状态码的意思就是"你发得太快了"。

一小时内已经发过 10 条，同样用 429 拒绝，逻辑上跟前一条是两道独立的关卡。

⚠

这道关卡关服务器重启就没了

postRateByIp 只是一个存在内存里的普通对象，不是数据库表。服务器一重启，所有人的发送记录全部清零——这也是 README 里强调"不把 IP 存进 SQLite"的原因：这份记录本来就只是临时挡一挡，不是要长期追踪谁。

第三关：证明你是人，不是脚本

光靠限流还不够——一个脚本完全可以每 11 秒发一条，慢慢刷屏。所以真正发消息之前，页面会先问服务器要一道随机的加法题。

server.js:53-60

function makeHumanCheck() {
  const a = randomInt(2, 12);
  const b = randomInt(1, 12);
  const token = `${Date.now().toString(36)}-${Math.random().toString(36).slice(2, 12)}`;
  const answer = String(a + b);
  humanChecks.set(token, { answer, expiresAt: Date.now() + humanCheckTTL });
  return { token, question: `${a} + ${b} = ?` };
}

随机出两个数字，凑成一道加法题，对一个真人来说毫不费力，对没有专门适配的脚本却是道坎。

token 是这道题专属的一次性凭证，混进了当前时间和一段随机字符，几乎不会跟别的题撞上。

正确答案连同这道题的TTL（有效期）一起，存进服务器内存里的 humanChecks，等着后面用 humanToken 来对答案。

只把题目和 token 送回前端，正确答案永远不会出现在发给浏览器的数据里。

还记得模块一里 server.js:158-169 那段代码吗？那里的 website 字段就是另一道关卡——honeypot（蜜罐）字段，人根本看不到它，只有不看页面样式、直接把每个输入框都填一遍的脚本才会中招。

第四关：前端画页面的时候也要挡一次

就算前面几关都被绕过、一条带着恶意代码的留言真的存进了数据库，app.js 在把它画到页面上时，还留了最后一道防线。

public/app.js:96-103

function renderItems(adminMode = false) {
  if (!dom.logFeed) return;
  dom.logFeed.innerHTML = state.items.map((item) => entryTemplate(item, adminMode)).join('');
  const blocks = dom.logFeed.querySelectorAll('.entry');
  blocks.forEach((entry, idx) => {
    const textEl = entry.querySelector('.message-text');
    textEl.textContent = state.items[idx].message;
  });

先用 innerHTML 一次性把外层卡片、按钮这些"骨架"画出来——这部分内容都是代码里写死的，不是用户能改的。

但留言正文没有跟着骨架一起用 innerHTML 塞进去，而是单独挑出来，逐条重新赋值。

关键就在这句 textContent：留言里就算写了一段像代码的文字，也只会被当成一串普普通通的字显示出来，不会被浏览器当真去执行。

✦

这道防线有个通用的名字

如果用户能提交的文字，被原样当成网页代码执行，攻击者就能在别人的浏览器里跑任意脚本——这类攻击统称XSS。这个项目挡它的办法很朴素：凡是用户自己写的内容，一律用 textContent 显示，绝不让浏览器把它当成标签解析。

小结

四道关卡从外到里排好队：Helmet 挡跨站脚本和乱七八糟的资源加载，限流挡疯狂刷屏，人类验证加蜜罐挡自动脚本，最后 textContent 在画面上再兜底一次。哪怕前面全部失守，最后一道也不会让恶意代码真的跑起来。

你写了一句完全正常、没有任何屏蔽词的留言，但连续点了 11 次 Transmit，第 11 次会发生什么？

用你自己的话说一遍：一条留言从发出到显示在页面上，一共要过哪几道防护关卡，每一道分别挡的是什么？

  • 提到了 Helmet 挡的是脚本和资源来源，而不是发送频率
  • 提到了 enforcePostRateLimit 按 IP 限制发送次数
  • 提到了人类验证和 honeypot 是两种挡自动脚本的不同办法
  • 提到了 textContent 是画面上最后一道防线
