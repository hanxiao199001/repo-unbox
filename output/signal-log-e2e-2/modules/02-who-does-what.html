地面站控制室里，都有谁在值班

认全这几个文件，以后加功能、抓 bug 才知道往哪个房间走

上一节我们看到，一条留言要经过三个文件才能真正落地。这一节把地面站控制室的门推开， 认全每个岗位——项目里一共五个主要文件，各管一摊，互不越界。

H

index.html

只画出页面骨架和空壳子——表单、按钮、留言区的位置，不管数据从哪儿来、往哪儿去。

A

app.js

收你敲的字，画出留言列表，负责跟后端搭话。它自己什么都不存，刷新页面就清空。

S

server.js

值班员——按你走的那条路把活派给对应的人，还要做防作弊检查，是这座地面站的门卫。

D

db.js

只有它碰硬盘。所有 SQL 语句、所有对 signal-log.db 的读写，都锁在这一个文件里。

C

styles.css

负责整站的深空视觉——导航条、信号格、按钮配色，不参与任何数据逻辑。

下面这几位要互相打个招呼。留意 server.js 提到的 路由（route） 和 GET 这两个词——你以后会经常在报错和文档里见到它们。

把 server.js 里真实的那段路由代码打开看看——它到底有没有自己去碰数据库：

server.js:148-156

app.get('/api/messages', (req, res) => {
  const limit = Math.max(1, Math.min(50, Number.parseInt(req.query.limit, 10) || 50));
  const offset = Math.max(0, Number.parseInt(req.query.offset, 10) || 0);
  const query = normalizeText(req.query.q, 100);
  const origin = normalizeText(req.query.origin, 64);

  const result = listMessages({ limit, offset, query, origin });
  return res.json(result);
});

app.get 挂了一条路由：只要有人访问 GET /api/messages 这个地址，就会跑这一段代码。

limit 和 offset 是分页用的两个数字，Math.max/Math.min 把它们框在合理范围里，防止有人传个负数或者一次要一万条。

query 和 origin 是搜索框和筛选按钮传过来的两个字符串，先经过 normalizeText 清洗一遍。

关键的一行：listMessages 才是真正去查数据库的函数，而它整个的定义都在 db.js 里，server.js 只负责把参数递过去。

res.json(result) 把查到的结果原样还给浏览器，server.js 没有对数据本身做任何加工。

✦

关注点分离

每个文件只管一件事：app.js 只管人机交互，server.js 只管路由和安全检查，db.js 只管数据。这个原则工程上叫关注点分离（separation of concerns），你可以直接拿这个词去问 AI：“这段逻辑该放在哪一层，会不会违反关注点分离？”

你想给每条留言加一个“编辑”功能，新逻辑主要应该写在哪两个文件？

如果 styles.css 里的颜色值写错了，会不会导致留言存不进数据库？

server.js 里几乎每个路由的最后一步，都是去调用 db.js 里的函数，这是为什么？

如果你想给每条留言加一个“点赞数”字段，你会怎么跟 AI 说，让它一次说清楚要动哪几个文件？把这句话原样写出来。

  • 点名了要在 db.js 的 messages 表里加一列，比如 likes
  • 点名了要在 server.js 里新加一个路由，比如 POST /api/messages/:id/like
  • 点名了要在 app.js 的 entryTemplate 里加一个显示点赞数的位置
  • 提到了这三层各管各的，不要让 app.js 直接去碰数据库
