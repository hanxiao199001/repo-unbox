02

谁在管这些频道

接收站自己不存东西，它只负责把每一单指到对的地方。

一台收音机上的几个频道

server.js 一共对外开了五条 API 路由（另外还有一个 /admin 管理页面，第五模块讲）。它们就像一台收音机上的几个频道，每个频道播的东西完全不同：

GET /api/human-check

要一道算术题。服务器出题，同时给你一张一次性票据。

GET /api/messages

要一页留言。可以带搜索词和来源筛选，一页最多 50 条。

POST /api/messages

发一条新留言。这是唯一要过全部反垃圾检查的一条路。

POST /api/report/:id

举报某一条。谁都能用，不需要任何身份。

DELETE /api/messages/:id

删掉某一条。唯一一条要管理员钥匙的路，第五模块讲。

每一条这样的约定，工程界叫一条路由。前面那个大写的词是方法，表示你想干什么。

最简单的一条：出一道题

server.js:143-146

app.get('/api/human-check', (_req, res) => {
  const challenge = makeHumanCheck();
  return res.json(challenge);
});

这一行声明：走 GET、地址是 /api/human-check 的，交给下面这段处理。

参数名前面那个下划线是约定俗成的记号，意思是“这个参数我用不上”。这里确实用不上，因为出题不需要看你是谁。

出一道题。返回的东西里有题面和一张票据。

直接把它当 JSON 发回去，这条路到此结束。

ℹ

下划线开头的参数

写成 _req 而不是 req，是在告诉后来的人：我知道这个参数在，但我故意不用。很多代码检查工具也认这个约定，不会再提醒你“有个变量没用到”。

复杂一点的一条：要一页留言

server.js:148-156

app.get('/api/messages', (req, res) => {
  const limit = Math.max(1, Math.min(50, Number.parseInt(req.query.limit, 10) || 50));
  const offset = Math.max(0, Number.parseInt(req.query.offset, 10) || 0);
  const query = normalizeText(req.query.q, 100);
  const origin = normalizeText(req.query.origin, 64);

  const result = listMessages({ limit, offset, query, origin });
  return res.json(result);
});

走 GET、地址是 /api/messages 的，交给这段。

这一行做的事比看上去多：把地址里带的 limit 变成数字，然后夹在 1 和 50 之间。有人手动把地址改成 limit=99999，也只会拿到 50 条。

offset 是“从第几条开始”。它和 limit 配合就是翻页：第二页就是 offset=50。

搜索词，最多留 100 个字符。normalizeText 会把多余空格压掉再截断。

来源筛选，最多 64 个字符。

空行，作者用它把“整理参数”和“真正干活”分开。

把四个整理好的参数交给日志本，让它去查。接收站自己一条数据都不碰。

查到什么就发回什么。

这条路结束。

⚠

别相信地址栏里的任何东西

limit、offset、搜索词全是用户能随手改的。这段代码对每一个都做了限制：转成数字、夹进范围、截断长度。凡是从外面来的值，先当它是恶意的。

03

怎么把机器人挡在外面

三道完全不同的防线，各挡一种人。

为什么留言板一定会被刷

任何人不用登录就能发的地方，一定会被自动脚本盯上。这个项目布了三道防线，而且三道挡的是完全不同的三种情况。

就像接收站上串起来的三个滤波器：一个滤掉发得太频繁的，一个滤掉根本不是人的，一个滤掉内容本身是垃圾的。

◔

限流

按 IP 数次数：两条之间至少隔 10 秒，一小时最多 10 条。挡的是“发得太快的人”。

◕

蜜罐

一个人类看不见的输入框。填了就直接判垃圾。挡的是“照着表单硬填的脚本”。

◑

算术题

服务器出一道加法，配一张五分钟过期的票据。挡的是“没有真正打开过页面的请求”。

第一道：数次数

server.js:87-92

  if (entry.lastPostAt && now - entry.lastPostAt < minGapMs) {
    return jsonError(res, 429, 'Rate limit: wait at least 10 seconds between transmissions.');
  }
  if (entry.recent.length >= maxPostsPerWindow) {
    return jsonError(res, 429, 'Rate limit: maximum 10 transmissions per hour.');
  }

如果这个 IP 上一次发言的时间还在，而且离现在不到 10 秒——

直接回 429。注意它给的是人话：“两次之间至少等 10 秒”，而不是干巴巴一句“被拒绝”。

第一道判断结束。

如果这一小时之内已经发过 10 条——

同样回 429，但换一句更准确的话。两种情况用同一个状态码，却给不同的解释，用户才知道该等 10 秒还是该等一小时。

第二道判断结束。

⚠

这份计数只在内存里

限流记录存在一个 Map 里，服务一重启就全没了。好处是不用存任何人的 IP，坏处是重启一次所有人的额度都清零。项目自己在 README 里写明了这个取舍。

04

日志本记在哪一页

留言存进 SQLite，信号强度是算出来的。

一个文件，就是整个数据库

上一门课里，待办是存在一个 JSON 文件里的。这个项目换了个更正经的东西：SQLite。

它的特别之处是：整个数据库就是项目根目录下的一个文件，叫 signal-log.db。不用装服务，不用配账号。你把那个文件拷走，数据就跟着走了。

它像一本装订好的台站日志本：每一行一条记录，格式固定，翻起来快，因为它自带目录。

db.js:6-14

db.exec(`
  CREATE TABLE IF NOT EXISTS messages (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    created_at TEXT NOT NULL,
    callsign TEXT,
    origin TEXT,
    message TEXT NOT NULL,
    strength INTEGER NOT NULL
  );

执行下面这段建表语句。

IF NOT EXISTS 的意思是“已经有了就别再建”。所以这段每次启动都跑，但只有第一次真正生效。

id 是主键，自动递增。第一条是 1，第二条是 2，你不用管。

创建时间，NOT NULL 表示必填，留空数据库直接拒绝。

呼号，没写 NOT NULL，所以可以留空。

来源，同样可以留空。

留言正文，必填。“哪些能空、哪些不能空”这件事，在建表时就定死了，比写在代码里的检查更靠得住。

信号强度，必填，是个整数。

这张表定义完了。下面还有一张 reports 表专门放举报。

信号强度是编出来的

页面上那个 0 到 100 的信号强度看着很酷，其实它不是测出来的，是按留言长度算出来的。

db.js:95-100

function computeStrength(message, id) {
  const len = message.length;
  const base = Math.min(85, 20 + Math.floor((len / 300) * 65));
  const noise = hashInt(id) % 16;
  return Math.max(0, Math.min(100, base + noise));
}

算强度要两样东西：留言内容和它的编号。

先量一下留言多长。

基础分：从 20 起步，按长度往上加，最多加到 85。写得越长，信号越强。

再加一点噪声：把编号哈希一下取余数，得到 0 到 15 之间的一个数。

两个加起来，再夹进 0 到 100。注意这个噪声不是真随机——它由编号决定，所以同一条留言算多少次都是同一个值。

函数结束。

✦

确定性（deterministic）

同样的输入永远得到同样的输出，这样的函数叫确定性函数。它的好处是可以随时重算、可以放心缓存、出问题也能复现。真用 Math.random()，同一条留言刷新一次强度就变了，看起来像 bug。

先写一行，再回头补一个字段

这里有一个先有鸡还是先有蛋的问题：强度要用编号来算，可编号是插入之后数据库才给的。

db.js:111-115

    const id = insert.lastInsertRowid;
    const strength = computeStrength(message, id);
    updateMessageStrengthStmt.run(strength, id);
    return getMessageByIdStmt.get(id);
  });

刚插入的那一行拿到了什么编号，数据库会告诉你。

有了编号，现在才算得出强度。

把算出来的强度写回那一行。所以一条留言其实被写了两次：先插进去，再补一个字段。

最后把这一行完整读出来还回去，页面拿到的就是带强度的版本。

这一整块被包在 db.transaction 里。事务的意思是：这几步要么全成，要么全不算。

⚠

没有事务会怎样

插入成功了、回填强度时程序崩了，数据库里就留下一条 strength 为 0 的残缺记录。事务的作用就是让这种“做了一半”的状态根本不存在。

05

值班室和出错的时候

谁能删留言，以及看懂那行英文报错。

一把钥匙，一道门

这个项目里，谁都能发留言、谁都能举报，但只有一件事需要身份：删除。

它没有账号密码，只有一把钥匙——一个写在服务器环境变量里的字符串。你把这把钥匙放进请求头里，门才开。这就像值班室的门：不问你是谁，只问你有没有钥匙。

server.js:132-141

function adminGuard(req, res, next) {
  if (!ADMIN_TOKEN) {
    return jsonError(res, 500, 'Admin token is not configured on server.');
  }
  const token = req.headers['x-admin-token'];
  if (!token || token !== ADMIN_TOKEN) {
    return jsonError(res, 401, 'Unauthorized admin token.');
  }
  return next();
}

函数名 guard 就是“守门的”。它是一个中间件，排在真正干活的代码前面。

先看服务器自己有没有配这把钥匙。

没配就回 500。注意这里是 500 不是 401：这不是你没带钥匙，是这扇门根本没装锁，属于服务器自己的配置问题。

这一段结束。

从请求头里把钥匙取出来。它叫 x-admin-token。

没带钥匙，或者钥匙不对。

回 401。401 的意思是“我不认识你”。

这一段结束。

两关都过了才放行，交给真正删除的那段代码。

函数结束。

⚠

这把钥匙不能写进代码里

它来自环境变量 ADMIN_TOKEN。写进代码就等于随着仓库一起公开了，任何人 clone 一份就能删你的留言。凡是密钥、密码、令牌，一律走环境变量。

所有的错都走同一个出口

server.js:285-289

app.use('/api', (_req, res) => jsonError(res, 404, 'API route not found.'));
app.use((err, _req, res, _next) => {
  console.error(err);
  return jsonError(res, 500, 'Internal server error.');
});

前面所有 /api 开头的路都没接住，就到这一行：回 404，而且是 JSON 格式的 404。这一点很重要——页面那边只会解析 JSON，回一段 HTML 它就懵了。

这一行是错误处理器。它靠参数个数被认出来：四个参数，不是三个。删掉最后那个看似没用的 _next，它就变回普通中间件，所有错误再也进不来。

把完整错误打进终端。这一行只印在终端，浏览器是看不到的。

对外只说一句 Internal server error。对内记全、对外说少，是安全上的常规做法。

错误处理结束。整个项目所有没被接住的错误，出口只有这一个。

这是留言板绕不开的一个问题：有人在留言里写一段脚本，别人打开页面就中招了。这个项目的处理方式在这八行里。

你最可能撞上的报错

下面四条都是这个项目真的会给出来的原文。左边一字不改，右边是中文意思和该怎么办。

{"error":"Rate limit: wait at least 10 seconds between transmissions."}

配合 429 出现。你两条留言之间隔得太近了，等 10 秒再发。这不是你写错了，纯粹是频率问题。

配合 400 出现。那道算术题超过五分钟没提交，票据作废了。刷新页面重新拿一道题就行。

{"error":"Admin token is not configured on server."}

配合 500 出现。服务器启动时 ADMIN_TOKEN 是空的。在 .env 里配上再重启——注意这是服务器的配置问题，不是你钥匙填错了。
