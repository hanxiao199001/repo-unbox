从“打字，点一下”到留言上墙

你亲手做过的这个动作，代码里到底发生了什么

打开 SIGNAL LOG 首页，你会看到一个深蓝色的收报台。左边是一张表： 呼号（callsign）、 来源（origin）、 留言正文。你在留言框里打上“Hello from orbit”，点下 Transmit 按钮——几乎是眨眼之间，这句话就出现在右边的 Live Log 里，带着一串闪烁的信号格。

SIGNAL LOG 骨子里是一本留言簿：谁都能匿名留一句话，所有人都在同一张列表里看到、搜索、举报，管理员还能把不像话的留言删掉。只是套了一层深空电台的外壳——留言变成了“电文”，人气变成了“信号强度”。

这门课从这一下点击开始，一路跟着这句话，看它到底经过了哪几个文件，最后停在了哪里。这一路要经过三个文件，先认识两个会反复出现的词： POST 是浏览器发请求时用的一种“方法”，意思是“我要新建一样东西”； 包裹（payload） 指的是请求里真正装的数据本身，就是你填的那几项。

app.js 里有一段专门处理这件事的 函数（function）， 名字就叫 submitTransmission。点“下一步”，跟着这句话走一遍它的全程。

整条路上，真正落盘的只有最后那一步。看看 db.js 里的 createMessage 长什么样：

db.js:102-113

export function createMessage({ createdAt, callsign, origin, message }) {
  const tx = db.transaction(() => {
    const insert = insertMessageStmt.run({
      created_at: createdAt,
      callsign,
      origin,
      message,
      strength: 0
    });
    const id = insert.lastInsertRowid;
    const strength = computeStrength(message, id);
    updateMessageStrengthStmt.run(strength, id);

createMessage：create（造一个）+ Message（消息），意思就是“造一条新留言”。它是 db.js 唯一负责往硬盘写东西的入口。

db.transaction 把接下来的几步打包成一个事务（transaction）：要么全部成功，要么一步都不算，不会出现“存了一半”的留言。

insertMessageStmt.run 才是真正往 SQLite 里写数据的那一行，参数用花括号一次性传进去，对应到 SQL 语句里的每个字段。

strength 先写成 0——这一步还不知道这条留言最终的信号强度是多少。

insert.lastInsertRowid 是 SQLite 自动生成的新留言编号，接下来还要靠它去更新这条记录。

computeStrength 拿着这条留言的文字和刚拿到的编号，算出一个 0 到 100 的信号强度分数。

updateMessageStrengthStmt.run 把算好的分数写回这一行，这时候这条留言才算真正“定型”。

把 server.js 里真实的那段路由代码打开看看——它到底有没有自己去碰数据库：

server.js:148-156

app.get('/api/messages', (req, res) => {
  const limit = Math.max(1, Math.min(50, Number.parseInt(req.query.limit, 10) || 50));
  const offset = Math.max(0, Number.parseInt(req.query.offset, 10) || 0);
  const query = normalizeText(req.query.q, 100);
  const origin = normalizeText(req.query.origin, 64);

  const result = listMessages({ limit, offset, query, origin });
  return res.json(result);
});

app.get 挂了一条路由：只要有人访问 GET /api/messages 这个地址，就会跑这一段代码。

limit 和 offset 是分页用的两个数字，Math.max/Math.min 把它们框在合理范围里，防止有人传个负数或者一次要一万条。

query 和 origin 是搜索框和筛选按钮传过来的两个字符串，先经过 normalizeText 清洗一遍。

关键的一行：listMessages 才是真正去查数据库的函数，而它整个的定义都在 db.js 里，server.js 只负责把参数递过去。

res.json(result) 把查到的结果原样还给浏览器，server.js 没有对数据本身做任何加工。

03

你在搜索框打了个词，服务器怎么听懂的

从地址栏里的一串问号，到数据库里的一句 SQL

你在搜索框里打上“orbit”，或者点一下 EARTH 这个筛选按钮，页面上的列表立刻变了——只剩下带这个词、 或者来源是 Earth 的留言。这背后到底发生了什么？

打开浏览器的开发者工具你会看到，实际发出去的地址变成了 /api/messages?limit=50&offset=0&q=orbit&origin=。 这一串问号后面的东西，叫 查询参数（query string）。 它就像图书馆检索台上填的那张卡片——你写下关键词和分类，剩下的翻找工作交给管理员，你自己不用挤进书库。

app.js 里有一个叫 originFilterValue 的小函数，专门把你点的那个筛选按钮翻译成一段查询参数： 点 EARTH 就翻译成 earth，点 CUSTOM 就翻译成你自己填的那个词。它自己不去查任何数据， 只负责把“你想要什么”说清楚，真正动手去数据库里翻找的，是下一屏要看的这个函数。

server.js 把这几个参数原样递给 db.js，真正“翻书”的活儿在这个函数里发生：

db.js:69-80

const listMessagesStmtFactory = ({ hasQuery, hasOrigin, unknownOriginOnly }) => {
  let sql = `
    SELECT id, created_at, callsign, origin, message, strength
    FROM messages
    WHERE 1=1
  `;
  if (hasQuery) sql += ` AND message LIKE @q`;
  if (unknownOriginOnly) {
    sql += ` AND (origin IS NULL OR TRIM(origin) = '' OR LOWER(origin) LIKE '%unknown%')`;
  } else if (hasOrigin) {
    sql += ` AND LOWER(COALESCE(origin, '')) LIKE @origin`;
  }

Factory 是“工厂”的意思——这个函数专门生产不同条件下的 SQL 语句。

sql 从一句最基础的查询开始： WHERE 1=1——这个条件永远成立，是故意留的占位符，方便后面用 += 一条条往后拼。

如果填了搜索关键词（hasQuery），就加一句 AND message LIKE @q。

如果筛选的是 UNKNOWN（unknownOriginOnly），就换一条完全不同的条件：来源是空的，或者本身就带着 unknown 这个词。

否则，如果填了具体的来源（hasOrigin），就加一句按 origin 模糊匹配的条件——两条件互斥，一次只会生效一种筛选方式。

✦

拼 SQL 不等于拼字符串

sql += ... 看着像是在拼字符串，但真正塞进去的值——@q、@origin——是命名参数占位符，不是把用户输入原样焊进 SQL 里。这样即使有人在搜索框里打奇怪的符号，也污染不了查询本身。这个技巧叫参数化查询（parameterized query），是防 SQL 注入的标准做法，你可以直接问 AI：“这段查询是参数化的吗，会不会有 SQL 注入风险？”

04

频段管理局：作者当时在防什么

一条留言要闯过五道关卡，才能真正被写进数据库

凌晨三点，一个脚本盯上了 SIGNAL LOG：它每秒钟往 /api/messages 灌一遍一模一样的留言， 想把 Live Log 刷成自己的广告牌。如果服务器什么都不做，数据库很快就会被灌满垃圾电文。

真实情况是，一条留言从进门到真正落进数据库，要闯过五道关卡——顺序就是 server.js 里代码真实的执行顺序：

1

发信频率检查（先于一切）

enforcePostRateLimit 是一段 中间件（middleware）， 在路由函数本身开始跑之前就先拦一道，超过 10 秒一条或者一小时 10 条，直接拒绝。

2

蜜罐字段 website

表单里藏着一个人看不见的 website 输入框，正常用户永远不会填它，只有无脑爬取表单字段的机器人才会填进去——填了就当场判定是机器人。

3

内容不能是空的或没有意义的符号

message 不能为空，还必须至少包含一个字母或数字——纯表情、纯空格都会被挡在外面。

4

不能是重复字符刷屏

isRepeatedSpam 检查这条留言是不是被某一个字符大量占据，比如两百个感叹号。

5

人机验证答案要对得上

最后核对一道算术题的答案，确认发信的是人，不是脚本。

先看第一道关卡——频率限制——真实的样子：

server.js:81-92

function enforcePostRateLimit(req, res, next) {
  const ip = getClientIp(req);
  const now = Date.now();
  const entry = postRateByIp.get(ip) || { recent: [], lastPostAt: 0 };
  entry.recent = entry.recent.filter((ts) => now - ts <= rateWindowMs);

  if (entry.lastPostAt && now - entry.lastPostAt < minGapMs) {
    return jsonError(res, 429, 'Rate limit: wait at least 10 seconds between transmissions.');
  }
  if (entry.recent.length >= maxPostsPerWindow) {
    return jsonError(res, 429, 'Rate limit: maximum 10 transmissions per hour.');
  }

getClientIp 取出这次请求是从哪个 IP 发来的，postRateByIp 这张表按 IP 记着“最近发过几次、上次是什么时候”。

entry.recent.filter 把一小时之前的旧记录清掉，只留下窗口期以内的。

第一道判断：离上一次发信还没满 10 秒（minGapMs），直接返回 429 这个状态码，配一句能在真实报错里原样看到的文案。

第二道判断：这一小时内已经发满 10 条（maxPostsPerWindow），同样返回 429，只是文案不一样。

拦住了机器人，还有最后一件事：就算是真人发来的正常留言，也不能被当成代码执行。看看 app.js 是怎么把留言正文画到页面上的：

public/app.js:96-103

function renderItems(adminMode = false) {
  if (!dom.logFeed) return;
  dom.logFeed.innerHTML = state.items.map((item) => entryTemplate(item, adminMode)).join('');
  const blocks = dom.logFeed.querySelectorAll('.entry');
  blocks.forEach((entry, idx) => {
    const textEl = entry.querySelector('.message-text');
    textEl.textContent = state.items[idx].message;
  });

先用 entryTemplate 拼出整段卡片骨架，塞进 dom.logFeed. innerHTML ——但这一步骨架里，留言正文那一格还是空的。

querySelectorAll('.entry') 把刚画出来的每一张卡片都找出来，准备逐个补上正文。

关键的一行：textEl. textContent = state.items[idx].message，把留言正文塞进去时用的不是 innerHTML，而是只显示纯文字的 textContent。

这一步是防 XSS 攻击的关键一步：如果有人在留言里打一段 <script>，用 textContent 显示出来的只会是一串没用的字符，不会被当成代码执行。

我在浏览器里点了两次 Transmit，后端返回了 Rate limit: wait at least 10 seconds between transmissions.，这是什么意思？帮我在界面上加个提示，让用户知道要等几秒。

I clicked Transmit twice and the backend returned Rate limit: wait at least 10 seconds between transmissions. What does this mean, and can you add a UI message telling the user how long to wait?

这个项目最可能撞上的几条英文报错，一字不改地列在这里：

Rate limit: wait at least 10 seconds between transmissions.

限流：两次发信间隔不到 10 秒。等 10 秒再试，或者对 AI 说：“帮我在提交按钮上加个倒计时，发完之后禁用 10 秒。”

Rate limit: maximum 10 transmissions per hour.

限流：这个 IP 一小时内已经发满 10 条。等一小时窗口过去，或者对 AI 说：“帮我把这个限额从 10 条改成 20 条。”

Human check expired. Request a new challenge.

人机验证的 token 已经超过 5 分钟没用，过期了。点一下“New”刷新算术题重新填，或者对 AI 说：“人机验证的有效期能不能延长到 10 分钟？”

Unauthorized admin token.

服务器启动时压根没读到 ADMIN_TOKEN 这个环境变量。检查 .env 文件是不是真的存在，或者对 AI 说：“帮我确认一下 ADMIN_TOKEN 有没有被正确加载。”
