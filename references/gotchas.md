# 翻车清单

> **什么时候读：** Phase 3（写模块 HTML）和 Phase 4（检查）。
> 每一条都来自真实产物里真实犯过的错，标注了是〔观察到〕还是〔推断〕。
> 〔观察到〕= 在某次生成的课程里实际发生过，有具体位置。〔推断〕= 根据原理预判，还没被真实撞到过。

---

### 1. 翻译带数量词的句子时，必须重新数一遍 〔观察到〕

英文原句里的数量，翻成中文之后往往不成立了。**中英文的计数单位根本不是同一个东西。**

> **v1 的实际错误：** 英文原稿写 `you type "buy milk"`，`buy milk` 是**两个词**。
> 中文写成“买牛奶”，是**三个字**。翻译时照抄了英文的语感，全课**五处**都写成了“这四个字”，
> 位置：模块 1 副标题、数据流动画的一条 label、输出题题干、对照清单里一项、正文一处。

同类高危：几行代码、几个文件、几条规则、几个参数、几步。
凡是句子里出现 `[一二三四五六七八九十两]+(个|行|条|份|站|道)`，**回去数一遍**。
`scripts/validate.mjs` 会把这类句子全部列出来供人工复核——它判不了对错，但能保证你不漏看。

---

### 2. 模板里的 HTML 注释会原样进产物 〔观察到〕

`references/_base.html` 曾经在导航区放了一段给模型看的英文说明
（`One <button> per module. Replace MODULE_N_NAME with...`）。
它被原封不动拼进了 `index.html`，出现在每一门课的源码里——学员按“查看网页源代码”就能看到。

**规则：给模型看的说明写在 `SKILL.md` 和 `references/*.md` 里，不要写在模板 HTML 里。**
模板里只留占位符本身。

---

### 3. 代码块必须是源文件里的连续行，逐字复制 〔观察到〕

这是 `CLAUDE.md`“代码一字不改”约束最容易被悄悄破坏的地方，
而且**人眼几乎发现不了**——改过的代码读起来更顺，反而更像对的。

> **v1 的实际错误：** 六个代码块有**四个**不合格。
> - 模块 1：删掉了 `try` / `catch` 六行。删掉的恰恰是“网络断了会显示报错”这个结论的唯一证据，
>   而同一个模块的测验题答案正依赖它。
> - 模块 2：把 `server.js` 里**不相邻**的六行拼在一起——真实源码里它们被注释、空行、
>   日志中间件和一个 health 路由隔开。
> - 模块 4：`create` 结尾的 `},` 写成了 `}`（差一个逗号）。
> - 模块 4：`persist` 删掉了原作者的注释行和一行 `await fs.mkdir(...)`。

**规则：**
- 每个代码块必须能在源文件里找到**连续的若干行**，逐字匹配
- **允许**整体去掉公共缩进；**不允许**改动相对缩进
- 需要展示不相邻的代码，就开**两个代码块**，各自连续，各自标注 `文件名:起止行`
- 每个块都要标 `文件名:起止行`，写在 `kc-code-pair__source` 里
- 原作者的注释是代码的一部分，**不要删**——它往往是最好的教学材料
- 觉得某段太长？**换一段**，不要裁剪它

写完自己跑 `node scripts/build.mjs <课程目录> --source <代码库路径>`，通不过不算写完。

### 4. 模型会去读校验脚本，然后对着考卷答题 〔观察到〕

第一次用真实仓库跑（`sdg5-hub/Signal_LOG` → `output/real-1`）时，模型在写任何模块之前，
先 `cat` 了 `scripts/validate.mjs` 和 `scripts/lib/code-check.mjs`，
整个会话里引用这两个文件 **14 次**。

它确实一次通过了全部校验——但它优化的对象是**检查脚本**，不是**规则本身**。
这两者只要有一丝缝隙，模型就会钻：比如 `data-kc-min` 只要是数字就过，
它可以填 10；清单只要 3–4 条就过，内容可以是废话。

**当前对策：** 规则的完整表述必须在 `content-philosophy.md` 和 `SKILL.md` 里，
校验脚本只是兜底，不是规则的定义。写检查时假设模型读过它。

---

### 5. 有旧课程在，模型会拿它当模板抄 〔观察到〕

同一次运行里，模型引用 `output/v1/` **24 次**，把它当作范例来对齐格式。
结果是比喻被整套搬了过来：**快递驿站、地铁、白板与档案柜**在两门课里都出现了，
尽管这两个代码库（待办 API vs 深空留言板）毫无关系。

`content-philosophy.md` 只禁止“同一门课里重复比喻”，没有禁止跨课程复用，
所以校验也拦不住。照这个趋势，这个 skill 产出的每一门课都会长得一样。

**没定的事：** 是该禁止读其他课程的产物，还是该维护一份“已用过的比喻”清单让新课避开。
撞到这条时没有改，先记下来。

---

### 6. 原生依赖不一定会在你的机器上失败 〔观察到〕

`better-sqlite3` 在 macOS ARM 上装得干干净净——`added 132 packages in 50s`，
因为它下载了预编译好的二进制，根本没编译。想拿到真实的编译失败原文，
必须**人为造一个没有 Python 的环境**（`env -i PATH=<只有 node 的目录>` 再跑 `node-gyp rebuild`），
才会出现 `Error: Could not find any Python installation to use`。

**规则：** 写“你最可能撞上的报错”时，报错必须是**你真的跑出来过的**，
并且要说清楚它**在什么条件下**才会出现。不要写成“npm install 一定会编译失败”——
那对一半的读者是假的。Windows 上缺 Visual Studio Build Tools 报的是另一条消息，
在 mac 上复现不了，就不要写进去。

### 7. `design-system.md` 一次都没被读过，后来被删了 〔观察到〕

第一次真实运行（`output/real-1`）的全程记录里，`references/design-system.md`（403 行）
**零次**被打开。SKILL.md 明写着“视觉规范见 `references/design-system.md`”，模型没理它，
转而去 `grep` 真实的 `references/styles.css`——四次，每次都只取片段
（`grep -n 'color-actor\|--color-bg' ...`、`sed -n '1005,1045p' ...`），
拿真实的 class 名和 CSS 变量。

**模型更信任源文件，而不是描述源文件的文档。**

**已处理（v0.2）：** 重写页面层之后，`design-system.md` 描述的那份实现已经不存在了，
留着就是一份会骗人的文档，所以删掉。视觉规范拆成两处：规则表述在 `spec/typography-zh.md`，
具体数值在 `references/styles.css` 顶部的 `@layer tokens` 块里——
**让模型直接 grep 源文件，这本来就是它在做的事。**

### 8. 拆分参考材料能减少一次性加载，但减不了总账 〔观察到〕

把 `interactive-elements.md`（1050 行）拆成 18 个按需加载的文件之后，同一个仓库、同一个模型：

| | 拆分前（real-1） | 拆分后（real-2-opus） |
|---|---|---|
| cache write | 158,649 | **137,192**（−13.5%） |
| cache read | 2,751,962 | **3,360,935**（+22.1%） |
| 轮次 | 29 | **36** |
| 费用 | $4.5422 | **$4.5513** |

**一次性灌进去的量确实降了，但轮次从 29 涨到 36，每多一轮就把已有上下文重读一遍，
省下的全被 cache read 吃回去。** 最后总价一分钱没变（差 0.2%）。

真正的成本动因是**轮次**，不是单份材料的大小。按需加载的价值在于"模型不必被无关内容干扰"，
不在于省钱——**不要再拿省钱当拆分材料的理由**。想降成本得减少来回，不是减少每次读的字数。

### 9. 强模型会自觉补上规则没写的东西，从而掩盖校验缺口 〔观察到〕

同一份 skill、同一个仓库，Opus 和 Sonnet 各跑一次：

| | Opus | Sonnet |
|---|---|---|
| 找 bug 元素 | **4 处**（没人要求） | **0 处** |
| 每模块代码块 | 5 个模块都有 | 第 6 个模块 **0 个** |
| 每模块中文字数 | 全部 ≥800 | 3 个模块 700–790 |
| 标点 | build 之前主动跑 perl 批量规范全角 | 撞到校验失败才逐处手改 |

这些当时**全都能通过校验**——因为校验查的是全课总数，而 Opus 自觉把每个模块都写扎实了，
缺口从来没暴露过。是 Sonnet 把它们一次性顶了出来。

**规则：校验要按最弱的模型设计，不是按你手边跑得最好的那个。**
用强模型验证一条新规则"够不够"，得到的答案永远偏乐观——它会替你把没写的部分补上，
让你误以为规则已经完整。每加一条约束，都要问一句：如果模型偷懒到极限，这条还拦得住吗？
